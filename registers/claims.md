# Claim register: where each claim is used

Baseline: the handoff register reviewed 2026-10-26. The same records (20 reviewed then, C21 added on 2026-10-30) ship as `spk.website.claim` data (`addons/spk_website_v2/data/website_claims.xml`) so editors maintain them in Odoo. Evidence references (P01–P18, S10) point to the internal source register, which is not part of this repository.

**Change of 27 October 2026.** The owner stated that every reader can act as a Thread Border Router and as an element of the Thread mesh, without separate firmware versions. C13 was moved from fallback to published, C14 (shared uplink) follows from it with its limits kept, and every page, table, FAQ and guide that used the old fallback was updated in the same change.

**Change of 27 October 2026 (C05, card programming).** The owner confirmed that SmartphoneKey does not support third-party card-programming devices: card programming is an additional capability of supported SmartphoneKey reader configurations, not the main selling point. The earlier wording ("with a compatible programming device, including the reader's built-in programmer where available"; "a compatible programmer or the supported built-in reader programmer") implied external programmer compatibility or an extra purchase and is withdrawn everywhere: claim record, compatibility rows (MIFARE Classic, MIFARE DESFire EV3, physical NFC keys; card rows re-verified 2026-10-27), the MIFARE guide (operator flow now taps the card on the SmartphoneKey reader that supports programming), the setup rule, route metadata and the copy deck (`docs/site-v2/04-COPY-DECK-EN.md`, which lists the view strings that still carry the old wording). Evidence for the clarification: owner-stated, 2026-10-27; it is not recorded as newly hardware-tested. The family names and the "not every configuration, no other generations or sizes" limits are unchanged.

**Change of 30 October 2026 (C21, Admin Panel AI Assistant; real screenshots).** Seven screenshots captured in the owner's browser from the production host (`docs/site-v2/assets/product-ui-2026-10-30/`, manifest beside them) show a built-in **AI Assistant** in the Admin Panel (v1.113.1) with its greeting and message field. The register gains C21 for it. The model's evidence enum has no "UI-observed" value; the record is stored as `code_supported`, the nearest level (a deployed interface was observed, not documentation), and the observation with its limits is written into the record. Allowed sentence: "Get help in the Admin Panel with the built-in AI Assistant. Available actions depend on your permissions and site configuration." Not evidenced: that any command works, example commands with results, delivery time, permission enforcement, door operation. The assistant, the SmartphoneKey app in ChatGPT and the visitor-facing AI Concierge (C17) stay three separate things. The same package supplies the first genuine Admin Panel screenshots (Dashboard, Assign Key wizard at step 2 with an empty recipient, Devices filters, Recent activity, Guest Key form in Wallet Key mode with a blank recipient): interface evidence for C01, C06, C07, C08 and C18 as already scoped. The figures visible in them are interface values from a test account and are not used as metrics.

Publication states: **public_scoped** (published with its limits), **fallback_only** (only the fallback sentence), **omit_numeric** (no number anywhere), **availability_enquiry** (ask-about-availability wording), **document_links_only** (documents, no badge).
